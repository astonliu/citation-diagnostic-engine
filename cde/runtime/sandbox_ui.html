Judgment Bench

Authors one cre_sandbox_packet_v1 of synthetic data, refuses it for every reason the engine would refuse it, runs it through the real F3–F7 band, and reads the record back. The page itself never judges. It has no model and no opinion — every verdict below is the engine’s, and this page only makes the packet honest going in and legible coming out.

Taxonomies

F1, F2 and F8 are not band taxonomies and cannot be selected here. They are existence and metadata faults — a dead or mismatched PMID, a retracted source — decided upstream by Band 1, and the band only ever sees a row they already cleared. This run skips that gate exactly as before, so the packet you author is judged as if it were already cleared. Give it a cited work production would have excluded and it will still answer, with an F3–F7 verdict that could never have been asked for.

What is new is that you can now put the same pair to the real gate as a separate question — see Band 1 in the right-hand column. It runs the same run.process_reference a corpus run calls, and it tells you whether the verdict below is one production could ever have produced.

Fill the pair from a real paper

Everything below this section is yours to type, and synthetic input is the point of the bench — the band judges the text in the packet, so a pair you invented gets a real verdict about real prose. What it cannot give you is a real document: markers, sentence boundaries, the section a claim came from, the seven other references cited in the same sentence, and what the cited paper actually says. Load a PMC article and this fills those in from the same parse_pmc_xml a corpus run uses.

The pair

The cited work

F3 requires · provenance is unanswerable without the cited work's own bibliography

F5 requires · supersession is a question about a point in time

Retrieval runs two streams, pubmed_esearch_claim and pubmed_esearch_mesh. With no MeSH terms the second query is empty, so F5 answers on half its retrieval — and the record cannot say so, because nothing was asked.

The cited work joins the bank automatically as its own row, because the evidence builder fetches it by PMID. It must not also appear as a candidate — nothing supersedes itself.

F7 requires · entity attribution reads body text, and only body text

F7 admits methods, results, table and figure. Never the abstract, introduction or discussion — those are where authors restate other people's findings, which is the thing F7 is trying to catch.

Synthetic paper bank

Every field matches a real PubMed record, so a synthetic candidate is indistinguishable in shape from a fetched one — the content is yours, which is the point. Each paper keeps a stable id; an F5 packet references it by that id.

Band 1 · would this pair reach the band at all?

A different engine and a different question. run.process_reference — the same per-reference function a corpus run calls for every row — asks whether the cited work exists (F1), whether it is the work the reference claims (F2), and whether it was retracted before it was cited (F8). A pair it faults never reaches F3–F7 in production, whatever the band would have said about it.

This one is live and this one is now. The band judges the text in your packet and would give the same answer next year. The gate asks PubMed, Crossref and OpenAlex what they hold today. A PMID you invented does not exist, so the gate will look, find nothing, and return F1 or a held state — correctly. That is a fact about the identifier, not about the citation you were modelling. Load a real paper on the left if you want this answer to be about your claim.
